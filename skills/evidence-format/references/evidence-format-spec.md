# Evidence 格式化规范：模板、槽位与反例

本文件是 `evidence-format` skill 的权威模板。所有格式均与 kb server（`re-mod-kb`）的解析契约对齐。

## 1. 文件级认识状态声明

**位置**：文件头部元信息区——h1 标题之后、第一个 `##`/`###` 之前，与"萃取日期/来源/原则"并列。

**标准文本**（模式/定案型文件）：

```markdown
- 认识状态：本库模式全部萃取自他人 mod 的静态审查（review）。各节"效果"行的标注体系——【实测】=有实机 capture 佐证、【裁决】=多方意见统合裁决、【源码】=源码级审查确认、【推断】=无直接证据的推断。【源码】级含义：源 mod 的写法与 review 判定已核实，但**未在本工作区实机复现**，复用到新项目后应按 evidence 规范补实机验证并更新状态。节头状态行仅在该模式有实测佐证或硬性条件限制时出现，无状态行的节默认为【源码】级。
```

项目自有调查文件（非 review 萃取）把首句换成对应来源描述即可，标注体系与"未实机复现"含义保留。

**项目自有且已实机验证的文件**（发布说明、实测定案记录）：照搬"未在本工作区实机复现"会与正文自相矛盾。用替代骨架——保留"分档声明 + 权威口径"结构，去掉"未复现"措辞：

```markdown
- 认识状态：本文件为<项目名>自有的<发布说明/定案记录>（<日期>），非 review 萃取。证据分档：标「实测定案」的结论依据<测量/对照的具体依据>；标「实机验证」的部分为<谁在什么环境观察>；其余各节为构建记录与文档指针。
- 认识状态说明：本文件不使用【实测】/【裁决】/【源码】/【推断】标注体系，证据等级以节标题字样与节头状态行为准；统一声明中"无状态行的节默认为【源码】级"**不适用于本文件**，本说明为本文件的权威口径。
```

文件内的分档字样（「实测定案」「实机验证」等）是什么就引什么，不发明新等级。

**覆盖行**（文件内标注体系与默认规则冲突时，追加在声明之后）：

```markdown
- 认识状态说明：本文件五节效果均为【推断】（蓝本应用未实机），统一声明中"无状态行的节默认为【源码】级"**不适用于本文件**，以各节效果标记为准。
```

- server 取 `- 认识状态` 开头的最后两行作为文件级口径，随 `kb_search`/`kb_read` 返回——**覆盖行必须放在声明之后**。
- 运行时口径（meshgroupmanager 式"本 mod 无 capture，性能量级均为推断"）同样走覆盖行，并注明"本说明为本文件的权威口径"。

## 2. 两分区结构（模式/定案节）

```markdown
### 3. 类型守卫的配置合并（旧配置不得用标量覆盖新默认表）
- **原版问题**：浅层合并（`for k,v in pairs(loaded) do default[k]=v end`）会让旧 config 的
  标量覆盖新默认值的表字段——数组/标量互换、缺键的旧配置直接污染运行期配置。
- **模式做法**：<原"实现方式"内容原样迁移：说明 + 代码块 + 行号指针>
  `xxx.lua:113-120`（同函数相邻行为的精确指针格式保留）
- **效果**：【源码】review.md:43："……"（标注体系原样保留）
- **复用提示**：<原样保留；适用范围与代价信息在这里展开>
```

要点：

- **原版问题**只能从原文"目的"字段或 review 记录显式化——把"避免…/不应…/不能…"改写成"默认写法下会发生什么"。**禁止编造原文没有的事实**。原文确实没有问题陈述时写 `- **原版问题**：见来源 review（原文未记录显式问题）`。
- 一般风险与历史故障要区分：有原版代码/日志支持的照写；仅从模式反推的措辞用"解决的问题/未采用该模式时的风险"，不写成"曾发生过"。
- "目的"字段信息被"原版问题 + 模式做法"覆盖后删除；有超出问题陈述的信息（适用场景等）并入不丢。

## 3. 节头状态行（三槽位，例外制）

紧跟节标题行（标题下一行，空行可有），`>` 引用格式，server 正则 `^\s*>\s*\[状态[：:]`：

**槽位**：①可行性（[状态：…]）→ ②代价/条件 → ③现行定案指针（被推翻时）。

| 场景 | 格式 |
| --- | --- |
| 实测佐证 | `> [状态：含实测佐证] <引用哪个实测，含归因边界>` |
| 硬性条件限制 | `> [状态：条件受限] <一句话条件>` + `> [代价/条件] <具体代价/降级行为>` |
| 被推翻 | `> [状态：已推翻] <一句话现状>` + `> [代价/条件] <残留有效性>` + 当前定案指针 |
| 部分有效 | `> [状态：部分有效] <哪些成立哪些不成立>` + 指针 |

真实例子（公区 better-matchmaking）：

```markdown
### 2. 统一 hook 安装收口（method 缺失/安装失败返回 false）

> [状态：含实测佐证] 已知副作用经实机确认：所有 hook 经同一 utils 闭包注册后，profiler 的
脚本归属显示为 utils.lua 而非各功能模块——排查时按 hook 的 event 名区分模块。

### 5. 线程感知的可重入守卫（重发调用不得覆盖请求快照）

> [状态：条件受限] `thread` API 在旧 nightly 可能缺失。
> [代价/条件] 回落 "default" 单键后退化为全局互斥（不崩，但并发语义变粗）。
```

**克制规则**：状态行总数 ≤ 总节数 40%（抽查口径）。全文件同类状态时用文件头覆盖行承担，不逐节铺。状态行一句话说完，写长了读取者会跳过它直接读正文，拦截失效。标题与状态行之间的空行可有（server 节头收集接受"标题 + 空行 + `>`"）；"已知限制"类节不加状态行——内容近乎复述正文时即仪式化，由文件头声明覆盖。

**时间线型定案节**（不重排正文的轻量增强）：

```markdown
### 8.1 F5 实测结论（日志 10414-10435，用户观感印证）
> [状态：实测通过] 2026-10-23 23:14 局定案；后续演化见 §9.6
```

## 4. 推翻指针（append 语义下的状态修正）

新定案推翻旧结论时，在**旧节头部**加状态行（不是节尾），正文保留：

```markdown
### 8.1 F5 实测结论（日志 10414-10435，用户观感印证）
> [状态：已推翻] prime 放宽对布局无效；当前定案见 §9.6「F10b conv 定案 + F11 帧源切换」。
> [代价/条件] 帧源切换后 conv 表需随游戏版本复核。

（原正文不动）
```

改的是认识状态，不是历史事实；kb 检索命中旧节时状态行置顶返回。

## 5. 跨文件时间线联动（release 系列与 test 序列）

同主题跨文件演化（bake2.1→2.2→2.3、test8→test16）中，**后发文件修正前文件定案**时，前文件按以下规则处理（kb 检索会同时命中系列全部文件，读者必须能从状态行看出哪份是现行定案）：

1. **扫描修正信号**：在后发文件里 grep "实测发现…仍/未/只"、"扩为/取代/作废/一次修全"、"重新扫描"、基线行（"基线：bake2.2 →"）。
2. **被修正的前文件**：相关定案节状态行从正面状态降级为 `部分有效` 或 `已推翻`，代价/条件行写明修正内容，指针指向**后发文件的文件名**（跨文件指针）：
   ```markdown
   > [状态：部分有效] 2026-10-10 用户手工实机；探针读数为同轮实测。
   > [代价/条件] 修复面不完整——bake2.3 实测发现其余 46 槽仍钉脚并扩为全清，
   > 现行定案见 `evidence-bake2.3gh说明-2026-10-11.md`。
   ```
3. **文件头声明补"时序位置"段**：一句话说明本文件在系列中的位置（中间态/最终态/被取代），现行定案指针。
4. **对象版本不同的不算推翻**：分析 2.x 版机制 vs 分析 3.0 版机制是两个对象，各自有效，靠声明中的对象与日期区分。
5. **终态文件**（系列最后一版、重新扫描归零）不用加"时序位置"，正常状态行即可。
6. **前文件的实测数据不降级**：数据是真的，降级的是"结论覆盖面/现行有效性"——措辞写"实测为真，但修复面/结论范围被后续修正"。

真实案例：FAR bake2.2（"清喝药三段修复脚贴地滑"含实测佐证）被 bake2.3（"翔虫拾取等仍钉脚，49 槽全清"）修正——bake2.2 状态行已改"部分有效"并指向 bake2.3，声明补时序位置段。

## 5b. 证明范围对齐（观察 vs 结论）

- 测量值照抄（`0.105 ms/帧`），评价性措辞单独标来源（"接近合理下限"= 审查判断 + 依据）。
- 整入口实测值（如 on_frame 总成本）引用时必须注明"不可分离归因于本节模式"。
- 【源码】标注只涵盖源码能确认的部分；性能/效果评价无 capture 时按文件头口径降为【推断】。
- 效果行引用别处的整体实测 ≠ 本节模式被实测——状态行里写清归因边界。

## 6. 反例（实战踩过的坑）

1. 节头只有 `> [代价/条件] …` 缺 `[状态：]` 头行 → server 不解析，形同虚设。
2. 状态行写在节尾 → 读取者先读正文才见状态，拦截失效。必须紧跟节标题。
3. 统一声明与文件内实际标注冲突（全文件【推断】但声明说"默认【源码】级"）→ 必须加覆盖行。
4. 文件移动后相对链接断（索引在根、模式在 evidence/ 子目录，链接要补前缀）。
5. 索引规模口径写"共 21 份"但实际 19 份 + 2 待收编 → 会被检索成当前库存，应标"历史采集 vs 当前库存"。
6. 一次性把被推翻节的正文删掉重写 → 破坏 append 语义。只加状态行，正文不动。

## 8. kb 解析契约速查（server 侧实现，格式变更需双向同步）

| 结构 | server 行为 |
| --- | --- |
| `> [状态：…]` 节头行（正则 `^\s*>\s*\[状态[：:]`，仅节头收集） | 切块为 chunk.status_block；kb_search/kb_read 置顶返回；沿标题栈继承给子节 |
| `- 认识状态` / `- 认识状态说明` 文件头行 | 合并为 file_note，kb_search 尾部按 (项目,文件) 去重返回、kb_read 头部返回 |
| `### N. 标题` 编号节 | heading 纯节号查询精确匹配（"2." 不中 "12."/"2.1"）；文字查询 完整→前缀→子串 |
| ``` / ~~~ 围栏（含长度语义） | 围栏内不解析标题与状态行 |
